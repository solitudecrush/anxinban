## 第一部分：基础难度（1–6）

### A. 系统整体架构

**1. 请简述整套系统的整体架构，系统分为哪几个主要部分？**

**答：** 安心伴是面向养老社区的智能看护系统，整体为「端—边—云—端」四层架构：

1. **感知设备层**：ESP32 传感器（温湿度、床压、烟雾）、智能摄像头（跌倒检测、抓拍）、智能手表（心率/血氧/体温采集、SOS 按键）、家居设备（灯光、窗帘、蜂鸣器、门锁）。设备通过 WiFi 接入家庭网络。
2. **边缘网关层**：家庭 PC/本地智能体，负责与设备局域网内通信、汇聚转发传感器数据、执行云端下发的指令（命令轮询拉取）、语音意图识别、断网缓存与补传。
3. **云端后端层**：Spring Boot 后端（业务与数据中枢），提供 REST API（约 182 个接口）与 MQTT 设备接入，配套 MySQL（38 张表）、MQTT Broker（本机 1883 端口）、Python AI 服务（127.0.0.1:8000，对接 DeepSeek）、Nginx 反向代理（80 端口）。
4. **前端应用层**：Web 管理端（社区工作人员：老人档案、告警处理、工单派发、数据看板）与家属 App（健康查看、告警通知、服务申请、监控审批、SOS）。

数据流向：设备 →（MQTT/HTTP）→ 边缘网关 →（MQTT + HTTP 双通道）→ 云端后端 → MySQL 持久化，并反向通过 MQTT 指令/HTTP 命令轮询控制设备；前端通过 REST API 查询数据。

**2. 边缘网关和云端后端之间有几条通信通路，分别承担什么职责？**

**答：** 共有 **4 条通信通路**（2 条上行 + 2 条下行）：

| 通路 | 协议 | 方向 | 职责 |
|---|---|---|---|
| MQTT 数据上报 | MQTT over TCP (1883, QoS1) | 上行 | 网关/设备直连 Broker，发布传感器数据（`house/+/+/sensor/+/data`）、设备状态、事件告警（跌倒/闯入/紧急呼叫）、摄像头图片、智能体请求等主题 |
| HTTP 统一上报 | HTTP POST | 上行 | 网关通过公网 `POST /api/edge/data` 把 MQTT 原始消息包装后补传/上传（upload_id 幂等），支持 vitals/imu/fall/sos/device_status 五类消息 |
| HTTP 管理通道 | HTTP REST | 上行 | 网关心跳 `POST /api/local-agent/heartbeat`、批量数据 `/api/local-agent/data`、告警上报 `/api/local-agent/alarm-report`、图片上传 `/api/gateway/upload-image`、命令结果上报 `/api/local-agent/control` |
| MQTT 指令下发 | MQTT (QoS1) | 下行 | 云端向 `house/{houseId}/{room}/actuator/{deviceId}/cmd` 发布控制指令（蜂鸣器、摄像头抓图） |
| HTTP 命令轮询 | HTTP GET | 下行 | 网关轮询 `GET /api/local-agent/{agentId}/commands` 拉取待执行命令（当前存内存队列，全局返回） |

设计思路：**实时事件走 MQTT（低延迟、发布订阅），可靠补传与管理查询走 HTTP（易重试、易鉴权）**，两条上行通道互为备份。

**3. 云端后端项目技术栈是什么，后端主要分为哪几层，每层作用是什么？**

**答：** 技术栈：**Java 17 + Spring Boot 4.0.6 + Spring Data JPA + MySQL 8.0.33 + HikariCP + Eclipse Paho MQTT 1.2.5 + Jackson 2.18.5 + Bean Validation**，Maven 构建，单 JAR 部署。

分层（`src/main/java/com/anxinban/`）：

| 层 | 包 | 职责 |
|---|---|---|
| 启动层 | `AnxinbanApplication` | 应用入口，`@EnableScheduling/@EnableAsync`，排除 DataSource 自动配置（自定义数据源） |
| 配置层 | `config/` | 全局配置：DataSourceConfig（Hikari 连接池，最大 10 连接）、CORS、Jackson 2.x、静态资源映射（/uploads/**）、GlobalExceptionHandler 统一异常处理 |
| 接口层 | `controller/` | 仅做参数接收/校验（@Valid）与 ApiResponse 统一响应封装，不写业务逻辑 |
| 业务层 | `service/` | 核心业务逻辑，多表操作加 `@Transactional`，Service 间允许互相调用 |
| 数据访问层 | `mapper/` | Spring Data JPA Repository 接口（按命名规范称 mapper），方法名自动解析 SQL |
| 实体/DTO | `entity/` `dto/` | JPA 实体（与表一一对应）、请求/响应传输对象 |
| 物联网模块 | `mqtt/` | MqttClientService（客户端连接/订阅/发布）、MqttMessageConsumer（消息解析入库）、RuleEngineService（联动规则）、AIAgentService、DeviceSimulator（设备模拟器） |

调用链：`Controller → Service → Repository → MySQL`，Controller 与 Service 之间用 DTO 传参。

**4. 云端后端部署在什么位置，服务器配置是什么？**

**答：**

- **位置**：阿里云 ECS（运维手册记录公网 IP 120.27.129.78，域名 elderlyweb.cn），Ubuntu 22.04。
- **服务器配置**：2 核 CPU、1.6GB 内存（当前可用约 400MB）、40GB 系统盘（已用约 10GB，/var/www/anxinban-backend 部署于此）。

## 第二部分：进阶难度（7–21）

### A. 告警链路与设备状态

**7. 从设备发生跌倒告警，一直到 App 弹出告警提醒，请完整描述整条端到端链路以及每段使用的通信协议。**

**答：** 完整链路（以摄像头跌倒检测为例）：

1. **检测**：摄像头 AI 识别老人跌倒，组装事件消息（deviceId、room、description、imageUrl）。
2. **MQTT 上报**（协议：MQTT QoS1，经 1883 端口 Broker）：发布到主题 `house/{houseId}/{room}/event/fall-detection/alert`。
3. **Broker 转发**：本机 MQTT Broker（Mosquitto/EMQX）将消息投递给已订阅该主题的后端客户端。
4. **后端消费**：`MqttClientService.messageArrived` → 分发监听器：
   - `MqttMessageConsumer.handleFallDetectionEvent`：创建 `alarm_event`（type=fall-detection，risk=high，status=pending）+ 同步写 `notification` 记录；
   - `RuleEngineService.processFallDetectionRule`：向摄像头主题 `house/{houseId}/{room}/actuator/camera-{room}-001/cmd` 发布抓图指令（MQTT QoS1）。
5. **图片回流**（协议：HTTP）：摄像头抓拍后通过 `POST /api/gateway/upload-image`（multipart）上传图片 → 存 `uploads/snapshot/` 磁盘 + 写 `file_metadata` 表 + 回写 `alarm_event.snapshot_url`。
6. **App 弹窗**（协议：HTTP REST）：App **轮询** `GET /api/notification/unread-count` 与 `GET /api/notification/list`（或告警列表 `/api/alarm/list`）→ 发现新未读告警 → 弹窗提醒（当前无 WebSocket/推送，实时性靠前端轮询保证）。

**说明**：手表端跌倒则由 ESP32 手表 → 边缘网关 → 网关经 `POST /api/edge/data`（HTTP）上报 fall 事件，同样生成告警与通知，图片经网关上传接口回流。

**8. 边缘网关网络断开离线之后，整套系统会出现哪些现象？网关网络恢复之后数据如何处理？**

**答：**

- **断网期间的现象**：
  - 网关心跳停止：`/api/local-agent/heartbeat` 不再上报，`local_agent.last_heartbeat` 停留在最后时刻；
  - 设备在线状态停止更新：`device.last_online` 不再刷新（设备显示离线或停留在旧状态）；
  - HTTP 上报失败：网关侧积压缓存数据，云端收不到新体征/事件；
  - MQTT 通道中断：若网关直连 Broker 的链路也断，事件告警延迟；云端规则引擎收不到该户数据。
- **恢复后的处理**：
  - 网关恢复联网后**补传缓存数据**（按原 upload_id 重新 POST /api/edge/data）；
  - 后端幂等去重：`edge_ingest_record.upload_id` 有 UNIQUE 约束，已处理过的 upload_id 直接命中幂等返回成功（不重复入库），未处理过的新数据正常写入；
  - 心跳/状态恢复上报后，在线状态自动刷新。
- **注意**：断网期间的事件类数据依赖网关本地缓存能力，缓存策略由网关侧实现，云端只保证幂等安全，不负责补发。

**9. 项目如何判断设备在线、离线？是否实现完整的设备离线告警功能？**

**答：**

- **判断依据**：`device` 表的 `status`/`online` 字段 + `last_online`（最近心跳/上报时间）。更新途径：
  1. `PUT /api/device/{deviceId}/status` 主动上报在线状态；
  2. 边缘网关 `device_status` 消息（经 /api/edge/data）更新 online/battery/last_online；
  3. 网关心跳 `/api/local-agent/heartbeat` 更新 `local_agent.last_heartbeat`。
- **是否完整实现离线告警**：**没有**。`RuleEngineService` 的类注释中规划了"设备离线告警规则（关键设备长时间未上报时告警）"，但代码中**未实现定时扫描超时设备的离线检测逻辑**；MQTT 路径的 `handleDeviceStatus` 目前只打印日志、不更新设备状态（HTTP 路径正常更新）。即：设备状态可查询，但"超时未上报自动判定离线并产生 device_offline 告警"的功能尚未实现。

### B. 通信协议与报文处理

**10. MQTT 中后端是发布者还是订阅者？EMQX MQTT Broker 部署在哪里？后端订阅了哪些 MQTT 主题？**

**答：**

- **角色**：后端**既是订阅者也是发布者**。订阅：接收设备/网关上报的数据与事件；发布：向设备下发控制指令（蜂鸣器、摄像头抓图）和智能体响应。
- **Broker 部署位置**：与后端**同一台服务器**（`tcp://localhost:1883`）。文档与配置按 **EMQX** 设计对接，当前线上 1883 端口实际由 **Mosquitto** 进程监听（EMQX 与 Mosquitto 都是标准 MQTT Broker，协议兼容），生产扩容可替换为 EMQX 集群。
- **订阅主题（6 个通配主题，QoS=1，启动日志可确认）**：

```
house/+/+/sensor/+/data        # 传感器数据（温湿度/床压/烟雾/手表健康）
house/+/+/device/+/status      # 设备状态
house/+/+/event/+/alert        # 事件告警（指纹/门禁/跌倒/紧急呼叫）
house/+/+/camera/+/image       # 摄像头图片
house/+/agent/request          # 智能体请求
house/+/agent/response         # 智能体响应
```

- **发布主题**：`house/{houseId}/{room}/actuator/{deviceId}/cmd`（指令下发）、`house/{houseId}/agent/response` 等。

**11. MQTT 消息格式错误、字段缺失的时候，后端会如何处理？**

**答：** 采用**容错丢弃 + 日志记录**策略，绝不让单条坏消息阻塞整个消息通道：

1. **消息分发隔离**：`MqttClientService.messageArrived` 对每个监听器 try/catch，某个监听器抛异常不影响其他监听器。
2. **解析失败**：`objectMapper.readValue` 抛 `JsonProcessingException` → 被 onMessage 的 try/catch 捕获 → 记录 `log.error("MQTT 消息处理失败，主题：{}")`，**该条消息直接丢弃**，继续处理下一条。
3. **字段缺失**：大部分 DTO 字段直接取 null 容忍；关键容错点是时间戳——`parseTimestamp()` 对 null/空串/格式错误分两级回退（先试 ISO_INSTANT，再试 LocalDateTime，最后回退 `LocalDateTime.now()`），保证入库不因时间格式崩溃。
4. **未知类型**：未知传感器类型（temperature-humidity/bed-pressure/smoke/watch-health 之外）、未知事件类型、主题格式不匹配 → `log.warn` 丢弃。

**改进建议**：坏消息目前静默丢失，建议单独落"解析失败消息表"或重试主题，便于线上复盘。

**12. 后端接收边缘网关上报的 HTTP 报文，如何解决网络重传带来的重复上报问题？**

**答：** 靠 **upload_id 幂等设计**（`EdgeGatewayService` + `edge_ingest_record` 表）：

1. **先查**：Controller 在进入事务前先查 `existsByUploadId(uploadId)`，命中直接返回 `duplicate` 成功响应（不重复处理，快速路径）。
2. **事务内写**：未命中则进入 `@Transactional` 事务：业务数据写入（sensor_data/alarm 等）+ 幂等记录写入**同一个事务**，最后 `persistIngestRecord` 写 `edge_ingest_record`（upload_id 有 **UNIQUE 唯一约束**）。
3. **并发兜底**：两个请求同时到达时，后者插入幂等记录触发 `DataIntegrityViolationException` → 转 `DuplicateUploadException` → 返回 duplicate 响应，**事务整体回滚**，不会产生脏数据。
4. **客户端重试安全**：无论请求在哪一步失败（500），网关重发同一 upload_id 都是安全的——要么幂等命中，要么完整重做。

这也是为什么 `upload_id` 必须由网关侧为每条消息生成唯一值（如 UUID）。

### C. 后端分层与调用链

**13. 后端 Controller-Service-Repository 标准调用流程是什么，请举业务例子说明。**

**答：** 标准流程：`Controller（参数校验 + 响应封装）→ Service（业务逻辑 + 事务）→ Repository（JPA 数据访问）→ MySQL`。

**例 1：告警转工单**（`POST /api/alarm/{alarmId}/to-work-order`）
1. `AlarmController` 接收 alarmId，校验后调用 `alarmService.convertToWorkOrder(alarmId)`；
2. `AlarmService.convertToWorkOrder`：查告警 `alarmEventRepository.findByAlarmId` → 查是否已有工单 `workOrderRepository.findByServiceRequestId`（防重复）→ 按告警类型映射工单类型（fall→紧急巡检、health_abnormal→健康关注…）→ 构造 `WorkOrder` 实体 `workOrderRepository.save` → 更新告警状态为 handled；
3. 返回 `ApiResponse.success(...)`。

**例 2：边缘数据上报**（`POST /api/edge/data`）
1. `EdgeGatewayController.receiveData`：@Valid 校验 → `validateTopicTypeMatch`（topic 与 message_type 一致性）→ 幂等快查；
2. `EdgeGatewayService.process`（`@Transactional`）：路由 vitals/imu/fall/sos/device_status → 写 `sensor_data`/`alarm_event`/`sos_record` → 写幂等记录；
3. 异常统一由 Controller 映射为 400/404/422/500 响应。

**14. Service 层之间是否存在互相调用？某个 Service 出现异常故障，会对其他业务模块产生什么影响？**

**答：**

- **存在互相调用**，典型例子：
  - `EdgeGatewayService` → `AiForwardService`（AI 健康分析，失败回退 Java 规则）；
  - `LocalAgentService.reportAlarm` → `AlarmService.createAlarm`（网关告警入库）；
  - `DeviceUploadController` → `AiForwardService` + `AiAnalysisRecordService`（AI 分析记录落库）；
  - `AlarmService` → `ElderUserRepository`/`WorkOrderRepository`（跨表联动）。
- **异常影响分析**（当前代码的容错设计）：
  - **AI 类调用**：全部 try/catch 包裹，`AiForwardService.forward` 失败返回 null → 调用方回退 Java 规则引擎，**主流程不受影响**（双轨降级设计）；
  - **通知写入**：`createNotification` 均 try/catch 且仅 warn，通知失败不影响告警生成；
  - **告警主链路**：`AlarmService` 抛异常会沿调用链上传 → `GlobalExceptionHandler` 返回 500，但各 Service 事务独立（REQUIRED 默认传播），一个 Service 失败不会污染其他模块的数据，MQTT 监听器异常也已被隔离（不影响其他消息）。
  - **潜在风险**：Service 间直接依赖 Repository（绕过另一 Service）的做法使部分校验/业务规则无法复用，跨 Service 调用失败时若没做降级（如告警转工单），该接口直接 500，前端需重试。

### D. 启动流程与运行表现

**15. 后端启动完整流程是什么？启动日志中需要重点关注哪些关键信息？**

**答：** 启动流程（约 23 秒，启动日志顺序可验证）：

1. **JVM 启动 + Spring 容器初始化**：加载 `application.properties`（支持环境变量 DB_HOST/DB_PORT/DB_NAME/AI_SERVICE_BASE_URL 覆盖）；
2. **数据源初始化**：`DataSourceConfig` 创建 HikariCP（最大 10 连接）→ HikariPool 启动并建立首个连接（日志：`HikariPool-1 - Starting... / Added connection / Start completed`）→ JPA EntityManagerFactory 初始化（ddl-auto=none，不改表结构）；
3. **MQTT 客户端连接**：`MqttClientService.afterPropertiesSet` 连接 Broker → 订阅 6 个通配主题（QoS1）→ 日志逐条打印"已订阅 MQTT 主题…"；
4. **监听器注册**：`MqttMessageConsumer`、`RuleEngineService` 的 @PostConstruct 注册到客户端（日志：`已注册 MQTT 消息监听器`）；
5. **其他初始化**：AiForwardService 创建 HttpClient、StaticResourceConfig 创建 uploads 目录与默认头像、设备模拟器（默认关闭）；
6. **Web 容器监听 8080**：日志 `Started AnxinbanApplication in 22.841 seconds`。

**重点关注日志**：① `HikariPool` 是否成功建连；② `MQTT 连接成功/连接失败`（失败仅 WARN，应用继续启动）；③ 6 个订阅主题是否齐全、QoS 是否为 1；④ 监听器注册；⑤ 有无 `ERROR`（未捕获异常）；⑥ 最后的 `Started AnxinbanApplication`；⑦ 启动后访问 `GET /api/health` 验证 database=connected。

**16. 后端启动阶段，如果 MySQL 没有启动、EMQX 没有启动，后端分别是什么运行表现，为什么这么设计？**

**答：**

- **MySQL 未启动**：**应用启动失败**。因为 Hikari 连接池在启动阶段（JPA 初始化）就要建立首个连接（日志可见 `HikariPool-1 - Starting...`），连不上会抛 `PoolInitializationException`，Spring 上下文初始化中断，进程退出。这是 **fail-fast（启动即强依赖数据库）** 的设计——业务数据全部在 MySQL，没有降级意义，尽早失败便于运维发现。MySQL 恢复后重启后端即可。
- **EMQX/MQTT Broker 未启动**：**应用照常启动**。`MqttClientService.afterPropertiesSet` 捕获 `MqttException` 仅打 `WARN("MQTT Broker 连接失败…应用将继续启动，MQTT 相关功能不可用")`。这是 **graceful degradation（优雅降级）** 的设计——Web/HTTP 通道不受 MQTT 影响，健康检查仍可服务；Broker 恢复后需重启应用或手动触发重连（Paho 的 automaticReconnect 只对"已连接后断开"生效，初始连接失败不会自动重试）。

两种组件采用相反策略，反映了各自的依赖定位：MySQL 是数据命脉（挂了服务没意义），MQTT 是外围通道（挂了核心 HTTP 业务可继续）。

### E. 数据处理与业务一致性

**17. 传感器上报异常体征数据，后端如何处理这些异常值，是直接丢弃还是保留？**

**答：** **保留并标记，不丢弃**。处理方式：

1. **入库标记**：每条 `sensor_data` 都有 `is_abnormal` 字段，按业务阈值实时判定：
   - 心率 >120 或 <50 bpm、血氧 <95%、体温 >37.5℃ → 异常；
   - 环境温度 >35℃ 或 <10℃、湿度 >90% 或 <20% → 异常；
   - 烟雾状态为 alarm/low → 异常。
2. **联动告警**：异常数据在更高一层触发告警——手表健康数据本身不自动告警（仅标记），但边缘上报的 vitals 会经 AI 健康分析/Java 规则（血氧<92、心率>110/<50、体温>38/35 等阈值）生成 health_abnormal 告警。
3. **保留的价值**：原始异常值保留便于趋势分析、二次复核、AI 训练与误报回溯；只丢弃"格式错误"的数据（MQTT 解析失败），不丢弃"值异常"的数据。

**18. 告警记录和通知记录同时写入数据库，如果通知写入失败，当前代码会出现什么现象？该如何改进？**

**答：**

- **当前现象**：`MqttMessageConsumer.saveAlarmWithNotification` 先 `alarmEventRepository.save(alarm)` 再 `notificationRepository.save(notification)`，**两个写操作之间没有事务**。若通知写入抛异常：
  - 异常被 onMessage 的 catch 捕获打 error 日志，**告警已落库但通知缺失**——出现"告警存在、App 消息中心无通知"的数据不一致；
  - `EdgeGatewayService.createNotification` 则直接用 try/catch 包住，失败仅 warn，同样是告警在、通知丢，且**没有任何重试**。
- **改进方案**：
  1. **加事务**：把"告警 + 通知"双写放入同一 `@Transactional` 方法，保证原子性（要么都成功要么都回滚）；
  2. **事务发件箱（Outbox）模式**：事务内只写 `notification_outbox` 表，由异步任务投递通知（先写库再发消息，杜绝丢失）；
  3. **读时聚合**：App 通知列表改为从告警表实时聚合生成，从根源消除双写问题。

**19. 工单有哪几种创建方式？工单完整状态流转是什么样的？工单完成之后告警状态会不会自动同步更新？**

**答：**

- **创建方式（4 种）**：
  1. **手动创建**：工作人员 `POST /api/work-order`（类型：紧急巡检/健康关注/设备检查/日常关怀等）；
  2. **告警转工单**：`POST /api/alarm/{alarmId}/to-work-order`，按告警类型自动映射工单类型，且校验不重复创建（用 alarmId 存到 service_request_id 字段做关联）；
  3. **服务申请转工单**：`POST /api/service-request/{requestId}/convert`（家属申请 → 工作人员审批转为工单，或 reject 拒绝）；
  4. **SOS/紧急事件联动**：SOS 处理流程中创建告警并派发工单（文档设计的紧急响应链路）。
- **状态流转**：`待处理（pending）→ 处理中（processing）→ 已完成（completed）`。
  - 创建默认"待处理"；`PUT /api/work-order/{orderId}/assign` 分配处理人 → 状态变"处理中"；`PUT /api/work-order/{orderId}/status` 置"已完成" → 记录 completeTime。
- **完成之后告警同步**：**不会自动同步**。仅在"告警转工单"那一刻把告警状态置为 handled；此后工单状态的变化（处理中→已完成）**不会回写** alarm_event。若要联动，需要补充"工单完成 → 回写关联告警状态/处理备注"的逻辑。

**20. 当前项目没有集成 Redis，请说明计划引入 Redis 用来解决哪些业务问题？引入 Redis 之后数据读写链路会发生什么变化？**

**答：** 当前未集成 Redis（无依赖、无配置），规划引入主要用于：

1. **设备/网关在线状态**：心跳与在线标记高频更新（每次写 MySQL 无必要），改存 Redis（EXPIRE 自动过期判离线），定时刷回 DB；
2. **告警/通知实时推送**：App 当前轮询通知接口，可用 Redis Pub/Sub 或 Stream 做推送通道/通知队列，降低轮询压力；
3. **热数据缓存**：最新体征、看板统计、设备列表、老人档案等读多写少数据缓存，缓解 MySQL 压力（尤其告警/工单列表目前是全表查出内存分页，缓存后可大幅改善）；
4. **幂等与限流**：upload_id 幂等去重从"DB UNIQUE 约束"升级为 Redis SETNX 快速判定；接口限流计数；
5. **会话/token**：当前 token 是无状态假 token，引入 Redis 后可存真实会话/黑名单。

**读写链路变化**：读路径变为 `Redis（命中即返回）→ Miss → MySQL → 回填 Redis`；写路径保持"先写 MySQL，再删/更新缓存"（Cache Aside）；在线状态等高频写走 Redis，异步批量落库。引入后 MySQL 直读大幅下降，但需解决缓存与 DB 一致性（见第 28 题）。

**21. 文件图片存储在服务器本地磁盘，磁盘占满时后端上传会发生什么？本地存储存在哪些弊端？**

**答：**

- **磁盘占满时的表现**：`Files.copy` 抛 `IOException` → 上传接口返回 500「文件保存失败」，并尝试清理已写入的临时文件（`Files.deleteIfExists`）；**数据库元数据不会写入**（避免元数据与文件不一致）；应用本身不崩溃，但所有上传类功能（头像、网关抓拍图）不可用，且占满磁盘会影响 MySQL 写入与日志。
- **本地存储弊端**：
  1. **单点故障**：文件与后端同机，磁盘损坏即全部图片丢失，无冗余；
  2. **容量有限**：40GB 系统盘，图片增长快，需人工扩容；
  3. **无备份/无清理**：当前无自动文件清理策略，磁盘只涨不缩；
  4. **性能耦合**：文件 IO 与业务 IO 争抢磁盘带宽，影响数据库和日志性能；
  5. **迁移困难**：扩容/迁移需拷盘或 rsync，无法弹性扩展；
  6. **无 CDN 能力**：全国访问延迟高。
- **建议**：接入对象存储（阿里云 OSS/MinIO）+ 数据库存 URL，Nginx/OSS 直出静态资源。

## 第三部分：深度拔高难度（22–51）

### A. 性能与数据存储

**22. 设备上报数据后端是单条实时写入 MySQL，还是批量写入？大量设备并发接入会产生什么瓶颈，有哪些优化手段？**

**答：**

- **现状**：**单条实时写入**。所有路径（MqttMessageConsumer 的 save、EdgeGatewayService 的 saveSensorData、DeviceUploadController 的 saveSensor）都是逐条 `sensorDataRepository.save()`，无批量、无缓冲；MQTT 消息在回调线程内同步写库。
- **并发瓶颈**：
  1. **连接池限制**：Hikari 最大仅 10 个连接，并发写多时线程排队等连接（connectionTimeout 30s 内拿不到就报错）；
  2. **单条 INSERT 开销**：每条记录一次网络往返 + 事务提交，吞吐上不去；
  3. **MQTT 回调线程阻塞**：消息消费与写库串行，Broker 消息堆积；
  4. **表膨胀**：sensor_data 单条插入 B+ 树，量大后写入变慢、索引膨胀。
- **优化手段**：
  1. **批量写入**：MQTT 消费端引入缓冲队列，攒批后 `saveAll()` 或 JDBC `rewriteBatchedStatements=true` 批量 INSERT；
  2. **连接池调大**：10 → 50 并按监控调整；
  3. **异步化**：消息先进内存队列/消息队列（Kafka），工作线程异步写库；
  4. **分表/分区**：sensor_data 按时间 RANGE 分区或按月分表；
  5. **写优化**：关闭无关索引、调大 innodb_buffer_pool、binlog 合并；
  6. **读写分离**：报表查询走从库。

**23. 后端 QPS 大概多少，系统主要性能瓶颈点有哪些？**

**答：**

- **QPS**：项目未做压测，无官方数据。按当前规模（单实例、2 核 1.6GB、Hikari 10 连接、演示数据量）估计 Web 读接口几十～一两百 QPS 量级，传感器写入路径（同步单条写库）会更低，属于 demo/小规模商用水平。
- **主要瓶颈点**：
  1. **列表接口全表查出内存分页**：告警、工单等 `findAll()` 后在 Java 内存里过滤分页（AlarmService.listAlarms、WorkOrderService.listOrders），数据量一大就 OOM/慢响应；
  2. **传感器写入链路**：单条 INSERT + 回调线程同步执行，吞吐受限；
  3. **无缓存**：最新体征、看板统计每次都查库；
  4. **MQTT 处理串行**：消息到达 → 解析 → 写库 →（可能）AI 调用（最长 15s 超时）都在监听器线程；
  5. **内存小**：1.6GB 物理内存，JVM 堆默认偏小，GC 频繁；
  6. **无索引优化**：sensor_data 等高频查询字段的组合索引缺失。

**24. 老人数量上涨到 1000 人，从数据库、连接池、缓存、MQTT、应用实例、服务器硬件层面分别给出扩容方案。**

**答：** 1000 老人 ≈ 3000-5000 台设备、传感器数据量级 ×100，分层扩容方案：

| 层面 | 方案 |
|---|---|
| **数据库** | ① sensor_data 按时间 RANGE 分区（月分区）+ 冷热归档（90 天前移归档表/OSS）；② 读写分离（主库写、从库跑报表）；③ 加组合索引 (elder_id, sensor_type, timestamp)；④ 列表接口改 SQL 分页（LIMIT），消灭内存分页；⑤ 必要时按老人 ID 水平分库 |
| **连接池** | Hikari 上限调至 50-100（按实例内存核算），加连接池监控；多实例时总连接数 = 实例数 × 池大小，控制 ≤ MySQL max_connections |
| **缓存** | 引入 Redis：最新体征、看板统计、设备状态、在线标记（TTL 过期判离线）、upload_id 幂等 SETNX、限流计数 |
| **MQTT** | Broker 升为 EMQX 集群（3 节点），按 houseId 分主题分散负载；QoS 分级（遥测 QoS0、告警 QoS1）；订阅端异步化消费 |
| **应用实例** | 多副本部署（2-3 实例）+ Nginx 负载均衡；实例无状态化——命令队列从内存 ConcurrentHashMap 外置到 Redis/DB；健康检查配合注册中心摘除故障实例 |
| **服务器硬件** | 2 核 1.6GB → 4 核 8GB 起（实例扩容前先升配置）；系统盘换 SSD；MySQL 独立实例（8GB+、SSD、独立 IO）；上传文件迁 OSS |

**25. sensor_data 传感器数据表随着时间持续膨胀，会带来什么性能问题？分表、冷热归档如何落地实现？**

**答：**

- **性能问题**：① 查询变慢——按时间范围/老人查询需扫描更多页，索引变大（内存放不下）退化为磁盘 IO；② 写入变慢——B+ 树层级加深、页分裂频繁；③ 备份/恢复时间成倍增长；④ 磁盘占用；⑤ 全表统计类 SQL（看板）拖垮主库。
- **落地实现**：
  1. **时间分区（推荐先做）**：`ALTER TABLE sensor_data PARTITION BY RANGE (TO_DAYS(timestamp))` 按月分区，配合按分区裁剪查询（查询条件必须带时间范围），删除旧数据直接 `DROP PARTITION`（O(1)）；
  2. **冷热归档**：定时任务（可扩展 DataMaintenanceService 模式）把 90 天前数据 `INSERT INTO sensor_data_archive SELECT ...` 后从主表 DELETE，归档表可放慢盘/压缩存储；查询接口按"近热远冷"路由；
  3. **分表**：数据量更大时按 `elder_id` 哈希分表（如 16 张），应用层路由；
  4. **注意**：当前 `DataMaintenanceService` 的"每小时最多保留 5 条 + 30 天时间推移"是为保持**演示测试数据新鲜**设计的（会删数据），生产环境必须替换为正规的归档策略，不能沿用。
  5. **配套**：组合索引 (elder_id, sensor_type, timestamp) 替换单列索引。

**26. 后端数据库表之间的 ER 关系是什么？哪些表是系统的性能瓶颈表？**

**答：**

- **核心 ER 关系**（无外键约束，靠逻辑关联）：
  - `elder_user`（1）—（N）：`family_user`（家属绑定）、`device`、`emergency_contact`、`alarm_event`、`notification`、`work_order`、`sensor_data`（经 device 或直接）；
  - `device`（1）—（N）：`sensor_data`（device_id 关联，再由 device.elder_id 关联老人）；
  - `alarm_event` → elder_user / device；`work_order.service_request_id` 关联 `service_request` 或告警 alarmId（告警转工单时）；
  - `file_metadata` → elder_user / alarm_event（snapshot_url 回写告警）；
  - `sos_record`、`monitor_request`、`service_request`、`health_record` 均以 elder_id 关联老人。
- **性能瓶颈表**：
  - **`sensor_data`**：数据量最大、写入最频繁，第一瓶颈；
  - **`notification`**：每告警必写，App 高频查询（list/unread-count），量级大；
  - **`alarm_event`**：高频写 + 大字段（description/snapshot_url）+ 列表查询多（内存分页）；
  - **`edge_ingest_record`**：每条上报都写，长期膨胀（可定期清理已过期 upload_id）；
  - **`work_order`/`service_request`**：查询多、过滤条件多，目前全表查出内存过滤。

**27. 数据库告警与通知写入没有事务，会出现什么数据一致性问题？**

**答：** 会出现以下一致性问题：

1. **部分成功**：告警已落库、通知写入失败（异常被吞/被 log），产生"有告警无通知"，App 消息中心看不到新告警，家属可能漏接收关键提醒——这是最严重的；
2. **重复通知**：MQTT QoS1 消息重复投递时，两次都成功写入告警+通知（无去重），产生重复告警/重复通知；
3. **状态不同步**：告警处理状态（handled）与工单状态独立变化，工单完成后告警不回写（见第 19 题）；
4. **幂等与业务不同步**：`EdgeGatewayService` 事务内是完整的（幂等+业务+告警同一事务），但 MQTT 路径（MqttMessageConsumer）无事务，重试/并发下可能出现告警重复。
- **根治方案**：① 双写加 `@Transactional`；② 引入事务性 Outbox 模式；③ 通知表加 (elder_id, alarm_id, type) 唯一索引防重；④ 读时聚合替代双写。

**28. 如果后续接入 Redis，如何保证 Redis 与 MySQL 之间的数据一致性？Redis 崩溃之后系统还能不能正常工作？**

**答：**

- **一致性方案（Cache Aside 为主）**：
  1. **读**：先查 Redis，Miss 回源 MySQL 并回填（带 TTL，避免长期脏数据）；
  2. **写**：先更新 MySQL，再删除/失效 Redis 缓存（删缓存优于更新缓存，避免并发写覆盖）；
  3. **延迟双删**：高并发场景删除缓存后短暂延迟再删一次，抵消"读线程在删除前回填旧值"的窗口；
  4. **最终一致性兜底**：缓存 TTL 过期自然收敛；对账任务定期校验；
  5. 在线状态/计数等可容忍丢失的数据，允许"只写 Redis + 异步落库"。
- **Redis 崩溃后**：**系统仍能正常工作（功能降级、性能下降）**——前提是 **Redis 只做缓存/加速层，不做唯一数据源**：
  - 读请求全部回源 MySQL（响应变慢但正确）；
  - 若在线状态仅存 Redis 则暂时无法判定在线（降级方案：回退比较 device.last_online 时间戳）；
  - 幂等若用 Redis SETNX，需回退 DB UNIQUE 兜底（当前本来就是 DB 兜底，安全）；
  - 通知推送若走 Redis Pub/Sub，崩溃期间退化为轮询。
  - **设计原则**：核心数据必须落在 MySQL，Redis 挂了只是"慢"，不能"错"。

**29. 项目文件存储有没有按日期分目录？文件命名如何保证唯一性，有无自动文件清理策略？**

**答：**

- **目录结构**：**没有按日期分目录**。当前仅两级子目录：`uploads/avatars/`（头像）、`uploads/snapshot/`（抓拍图），文件平铺其中。建议后续改为 `uploads/snapshot/2026/08/13/` 便于归档与清理。
- **命名唯一性**：`fileId = "file_" + UUID 随机前 12 位` + 原文件扩展名（网关上传），头像为 `avatar-{UUID8位}{ext}`、快照为 `snapshot-{UUID8位}.jpg`。**UUID 随机性保证文件不重名**，且上传时不覆盖已存在文件（Files.copy 不带 REPLACE_EXISTING），文件名即主键（file_metadata.file_id）。
- **自动清理**：**无**。没有任何定时删除文件的策略（DataMaintenanceService 只清数据库时间数据，不动磁盘文件），磁盘只增不减，需补充"按创建时间清理 N 天前文件"的定时任务，或整体迁 OSS 后由对象存储生命周期策略管理。

**30. 网关上传图片元数据存放在哪张数据表，图片查询条件、URL 如何构成？**

**答：**

- **存放表**：`file_metadata` 表。字段：`file_id`、`elder_id`、`original_name`、`file_path`、`file_size`、`content_type`、`alarm_type`、`snapshot_time`、`created_at`。同时告警表 `alarm_event.snapshot_url` 保存该图片的相对路径（网关上传时传 alarmId 会回写）。

### B. MQTT 与消息可靠性

**32. 告警消息可靠性依靠哪些机制？MQTT QoS 1 起到什么作用？哪些场景下依然会出现消息丢失？**

**答：**

- **可靠性机制（多层叠加）**：
  1. **MQTT QoS 1（至少一次投递）**：Broker 收到消息回 PUBACK，发布端重发未确认消息，保证消息**至少**到达一次；
  2. **Paho 自动重连（automaticReconnect=true）**：连接断开后自动重连并恢复订阅；
  3. **数据库持久化**：告警/通知写入 MySQL，落库即不丢；
  4. **HTTP 通道幂等**：边缘网关走 /api/edge/data 时靠 upload_id 幂等去重，QoS1 的重复投递在业务层被消化；
  5. **双通道冗余**：MQTT 故障时网关仍可用 HTTP 上报。
- **QoS1 的作用**：把"网络抖动导致丢包"的概率降到最低（未确认即重发），但对应用层意味着**可能重复**，因此业务侧必须有幂等（upload_id / 唯一约束）。
- **仍会丢失的场景**：
  1. **Broker 宕机/重启期间**发布的消息：cleanSession=true，Broker 不持久化未投递消息；
  2. **订阅端（后端）断开期间**的消息：cleanSession=true 无持久会话，离线消息不保留，重启后从新订阅开始收（见第 36 题）；
  3. **发布端断线瞬间**未发出的消息（QoS1 只能覆盖"已发出未确认"，覆盖不了"压根没发出"）；
  4. **Broker 队列溢出**：Mosquitto 内存队列满后丢弃最老消息（max_queued_messages 默认 1000）；
  5. **QoS1 在极端断点**：连接断开与 PUBACK 交错时消息可能丢失（QoS1 语义本身允许这种边界）。
- **补齐方案**：关键告警再加 HTTP 上报通道、Broker 持久化配置、订阅端持久会话（cleanSession=false）。

**33. MQTT 协议 QoS0、QoS1、QoS2 分别代表什么含义，本项目选用的是哪一级，为什么没有全部使用 QoS2？**

**答：**

| 级别 | 语义 | 消息数 | 适用场景 |
|---|---|---|---|
| QoS0 | 最多一次（fire-and-forget，不确认不重发） | 1 | 可容忍丢失的遥测（温湿度、IMU） |
| QoS1 | 至少一次（PUBACK 确认，未确认重发，**可能重复**） | 2 | 不容丢但可容忍重复（告警、状态） |
| QoS2 | 恰好一次（PUBREC/PUBREL/PUBCOMP 四步握手，不重不丢） | 4 | 严格不重复不丢失（计费、支付） |

- **本项目选用 QoS1**（`mqtt.qos=1`，订阅与发布统一）：传感器数据与告警事件"**不能丢、但可以容忍重复**"——重复由业务幂等兜底（upload_id、通知唯一索引）。
- **为什么不用 QoS2**：
  1. **开销大**：消息确认次数翻倍（1 条消息 4 次往返），对低功耗嵌入式 ESP32/手表端和弱网环境不友好；
  2. **实现复杂**：设备端嵌入式 MQTT 客户端对 QoS2 的会话状态管理要求高；
  3. **无必要**：QoS2 解决的"恰好一次"问题，业务层用幂等去重同样能解决，且更灵活（幂等还能覆盖 HTTP 通道的重复）；当前告警链路没有"重复就会造成严重后果"的场景（不会重复扣费/重复派单到不同对象）。
  4. 高价值告警（跌倒/SOS）若未来需要更强保障，可单独把该主题升级为 QoS2，其余保持 QoS1。

**34. MQTT 消息生产速度大于消费速度，消息堆积会造成什么后果？可以采用哪些缓解手段？**

**答：**

- **后果**：
  1. **Broker 队列膨胀**：Mosquitto 每个订阅者维护队列，超出 `max_queued_messages`（默认 1000）后**丢弃最老消息**（静默丢数据）；
  2. **延迟增大**：消费侧排队，告警处理滞后，实时性丧失；
  3. **内存/磁盘耗尽**：Broker 内存占用飙升，极端情况 Broker OOM；
  4. **客户端重传风暴**：QoS1 未及时确认导致发布端不断重发，进一步加剧堆积；
  5. **数据新鲜度下降**：健康监测失去实时意义。
- **缓解手段**：
  1. **提高消费能力**：后端异步化消费（消息进内存队列/工作线程池），批量写库；
  2. **削峰**：引入 Kafka/RabbitMQ 做二级缓冲，Kafka 天然海量堆积（磁盘顺序写）；
  3. **降级**：非关键遥测（温湿度/IMU）降为 QoS0，只保留关键告警 QoS1；
  4. **限流背压**：消费侧设置最大队列长度，超限丢弃低优先级消息（带日志）；
  5. **Broker 扩容**：EMQX 集群横向扩展、按 houseId 分主题分担；
  6. **会话管理**：合理设置 cleanSession 与队列上限，避免无人消费的订阅者积压。

**35. 当前告警处理是同步执行业务逻辑，如果不引入消息队列会有什么风险？如果引入 Kafka，告警链路该如何改造？**

**答：**

- **同步处理的现状与风险**：MQTT 监听器线程内同步执行「解析 → 写 sensor_data → 写告警 → 写通知 → 可能调 AI（最长 15s 超时）」：
  1. **阻塞消息接收**：一条慢消息（AI 超时）卡住回调线程，后续消息全部排队，Broker 侧堆积甚至丢消息；
  2. **无重试机制**：写库/通知失败只 log，告警直接丢失；
  3. **故障放大**：MySQL 抖动一次，导致大量消息处理失败；
  4. **无法水平扩展消费**：单实例监听线程固定。
- **引入 Kafka 的改造方案**：

```
设备/网关 ─MQTT→ Broker ─→ 后端 MqttListener（只做解析+投递）
        ─→ Kafka topic: anxinban.device.data / anxinban.alarm.event
        ─→ 消费者组（可水平扩展）：
            ├─ 告警处理消费者：写 alarm_event（重试 topic + 死信队列）
            ├─ 通知消费者：写 notification / 推送
            └─ AI 分析消费者：调 Python AI（独立于主链路，慢不影响其他）
        ─→ MySQL
```

  收益：① 消费与生产解耦，MQTT 监听器只做轻量投递；② 削峰填谷，Kafka 磁盘堆积几乎无限；③ 失败可重试（重试 topic）+ 死信可复盘；④ 消费者组水平扩展；⑤ 消息可回放（出问题重放修复）。

**36. 云端后端实例宕机重启，MQTT 消息是否会丢失，取决于哪些 Broker 配置？**

**答：** 会丢失，但**取决于 Broker 配置**：

- **当前配置（cleanSession=true）**：后端断线期间，Broker 不保留该客户端的会话与未投递消息 → **重启期间的消息全部丢失**，重启后从重新订阅那一刻开始接收。
- **决定是否丢失的关键配置**：
  1. **cleanSession（清理会话标志）**：`false`（持久会话）时 Broker 保留订阅关系和离线消息，重连后补发；`true`（当前）则不保留；
  2. **Broker 离线消息队列**：Mosquitto 的 `max_queued_messages`/持久化（默认内存队列，重启 Broker 即清空）；EMQX 可配持久化（mnesia/磁盘）与 `session_expiry_interval`；
  3. **QoS 级别**：QoS0 消息在 cleanSession=false 下也可能不补发，QoS1/2 才会进离线队列；
  4. **Retained 消息**：只保留每个主题最后一条，非全量；
  5. **会话过期时间**：EMQX 的 session expiry interval，过期后持久会话也失效。
- **结论**：当前架构"重启即丢窗口消息"，关键告警建议：① 改 cleanSession=false + 持久会话；② 或设备侧重连后补发（HTTP 补传 + upload_id 幂等）；③ 或消费端 Outbox 落库后再确认。

### C. 故障与高可用

**37. 分别说明感知硬件故障、边缘网关故障、EMQX 故障、MySQL 故障、SpringBoot 后端服务故障，各自的故障影响范围。**

**答：**

| 故障组件 | 影响范围 | 恢复方式 |
|---|---|---|
| **感知硬件故障**（单个传感器/摄像头/手表） | 仅该设备数据缺失、相关告警漏报（如跌倒检测摄像头故障 → 该区域跌倒告警失效）；其他设备与业务正常 | 设备端修复/更换，自动恢复上报 |
| **边缘网关故障**（家庭 PC/本地智能体） | 该户整条数据链路中断：设备↔网关↔云端全部停摆，该户无新体征、无新告警，App 看到该户数据静止；其他户不受影响 | 网关重启/修复后，缓存数据补传（幂等去重） |
| **EMQX/MQTT Broker 故障** | MQTT 通道全断：设备直连上报与云端指令下发不可用；但**HTTP 通道仍可用**（网关仍可走 /api/edge/data、/api/local-agent/* 上报与轮询），Web/App 管理功能不受影响 | Broker 恢复后自动重连（Paho automaticReconnect）；注意 cleanSession=true 窗口期消息丢失 |
| **MySQL 故障** | **影响最大**：所有读写接口 500（登录、告警、健康查询全部不可用）；MQTT 消息处理写库失败（日志刷 ERROR）；但 Spring Boot 进程存活、/api/health 返回 database=disconnected，HTTP 端口可达 | MySQL 恢复后连接池自动重建连接，业务自动恢复；MQTT 窗口期消息可能丢失 |
| **SpringBoot 后端故障** | 全部服务不可用：Nginx 返回 502；MQTT 无消费者（消息堆积/丢失）；前端完全不可用 | systemd `Restart=always` 5 秒自动拉起；若启动失败（如 MySQL 未起）需人工介入 |

**关键设计结论**：MySQL 是唯一"挂了全瘫"的组件，最需要优先保障（备份、主从、独立部署）；Broker 挂了还有 HTTP 兜底，属于可降级组件。

**38. 数据库连接断开、MQTT 连接断开后端分别是什么行为，是否具备自动重试能力？**

**答：**

- **数据库连接断开（运行中 MySQL 故障/重启）**：
  - 行为：正在执行的查询报 `CommunicationsException`/`Connection is not available`，接口 500；HikariCP 检测到失效连接会剔除（evict），**后续请求自动从池中创建新连接**（Hikari 的 fail-fast 重建机制）。
  - 是否自动重试：**连接层面自动恢复**（池化天然具备），业务查询不重试（请求直接失败，由客户端重试）；MySQL 恢复后无需重启应用。
- **MQTT 连接断开**：
  - 行为：`connectionLost` 回调打 error 日志；Paho 配置了 `automaticReconnect=true`，**自动重连并重新订阅**（恢复订阅关系）；重连成功前，publish 会抛 `REASON_CODE_CLIENT_NOT_CONNECTED`（被调用方捕获记录日志）。
  - 是否自动重试：**断线后自动重连（是）**；但注意**初始连接失败不自动重试**（connect 失败只 warn，不会周期重试，需要重启应用或手动触发 connect）。
- 结论：两类连接都具备"运行中断开后自动恢复"能力，差异是 MySQL 恢复后业务立即可用，MQTT 重连存在窗口期消息丢失（cleanSession=true）。

**39. 告警处理流程中，如果数据库写入失败、通知处理失败，后端如何处理，告警是否会重试？**

**答：** 分三条路径（当前实现不一致）：

| 路径 | 数据库写入失败 | 通知写入失败 | 是否有重试 |
|---|---|---|---|
| **边缘网关 HTTP 上报**（/api/edge/data） | `@Transactional` 整体回滚 → 返回 500 → **网关重发同 upload_id（幂等安全）** | createNotification 被 try/catch 吞掉，仅 warn | **告警可重试（依赖网关重发）**；通知无重试 |
| **MQTT 消息消费**（MqttMessageConsumer） | 异常被 onMessage catch → log.error → **该告警直接丢失，无重试** | 双写无事务，告警已落库、通知缺失 | **无重试** |
| **规则引擎**（RuleEngineService） | 同上，异常被 catch 记录日志 | 同上 | **无重试** |

- **结论**：只有 HTTP 通道（网关侧重发）具备端到端重试能力；MQTT 通道的告警写库失败即丢。通知在任何路径都没有重试。
- **改进**：① MQTT 消费端引入重试队列/死信（Kafka 或 DB Outbox）；② 通知补发定时任务（扫描"有告警无通知"的记录）；③ 关键告警写失败时尝试 HTTP 报警渠道兜底。

### D. 架构与设计决策

**40. 本系统哪些业务属于边缘计算，哪些业务属于云计算？边缘与云端的任务划分依据是什么？**

**答：**

- **边缘计算（网关/设备端）**：
  1. 传感器数据**采集与本地汇聚**（ESP32 直连传感器）；
  2. 数据**转发与缓存**（断网积压、恢复补传）；
  3. **命令执行**（网关轮询云端命令队列，驱动蜂鸣器/灯光/窗帘/摄像头抓图）；
  4. **语音意图识别**（本地智能体解析老人语音并上报 intent）；
  5. 跌倒等事件的**本地初判**（摄像头端侧 AI、手表端 IMU 判定）。
- **云计算（云端后端）**：
  1. **规则引擎联动**（RuleEngineService：夜间离床、陌生人闯入→蜂鸣器+抓图、跌倒→抓图，部署在云端 Spring Boot 中）；
  2. **数据持久化与全局管理**（老人档案、设备台账、工单、通知）；
  3. **AI 深度分析**（Python AI 服务 + DeepSeek：健康风险评估、深度对话、RAG 知识问答、情绪分析）；
  4. **跨户全局业务**（看板统计、工单流转、告警处理、App 服务）；
  5. **设备远程控制中枢**（命令队列 + 指令下发）。
- **划分依据**：① **实时性**——要求毫秒级响应的就地处理（抓拍、报警联动）放边缘，可容忍秒级延迟的放云端；② **算力需求**——大模型推理需要云端 GPU/高性能，端侧做轻量初判；③ **数据量**——海量原始遥测在边缘聚合，云上只收关键数据；④ **离线可用性**——断网时边缘必须独立工作（告警提示、语音应答）；⑤ **全局性**——需要跨户/全局数据支撑的业务只能上云。

**41. 对比「边缘网关中转架构」和「设备直连云端 MQTT 架构」，两种架构的优缺点？**

**答：**

| 维度 | 边缘网关中转（本项目） | 设备直连云端 MQTT |
|---|---|---|
| **功耗/流量** | 设备只与网关局域网通信，省电省流量（适合电池设备） | 每台设备维持公网长连接，功耗与流量高 |
| **可靠性** | 网关可断网缓存补传（幂等去重），抗弱网 | 设备断网即丢数据（除非设备端自己缓存重传） |
| **安全** | 设备不暴露公网，攻击面小；云端只信任网关 | 每台设备直接暴露 Broker，需设备级证书/鉴权 |
| **协议统一** | 网关做协议转换（异构传感器统一接入） | 每类设备直接对接，协议异构难统一 |
| **实时性** | 多一跳，增加毫秒级延迟 | 最短链路，延迟最低 |
| **单点故障** | 网关故障导致整户离线（本项目最大弱点） | 无网关单点，任一设备故障只影响自身 |
| **部署维护** | 网关需部署、升级、维护，成本高 | 免网关，云端直接管理每台设备 |
| **扩展性** | 加设备只需接入网关，云端连接数少 | 设备数量直接压 Broker 连接数，需集群扩容 |

**结论**：本项目选边缘网关中转，核心考量是**电池设备（手表/传感器）功耗、弱网家庭环境（断网续传）、安全隔离**；代价是网关单点故障。折中方案：关键设备（手表 SOS、摄像头跌倒）支持双通道直连备份，网关故障时仍能上报。

**42. 为什么后端选用 Java Spring Boot，而不选择 Python、Node.js 技术栈？**

**答：**

1. **生态成熟**：Spring Boot 提供开箱即用的 Web/JPA/Validation/事务/定时任务全套，IoT 后端需要的组件（连接池、REST、消息）都有成熟集成，开发效率高；
2. **类型安全与工程质量**：Java 强类型 + 编译期检查，对老人/设备/告警这类强业务模型（DTO/Entity）友好，大规模重构可维护性远好于 Python/JS；
3. **并发与稳定性**：Java 17 + 虚拟线程/线程池适合 MQTT 回调、多路 HTTP 调用的 IO 密集场景；Node.js 单线程在 CPU 密集（JSON 解析、规则计算）下会阻塞事件循环；Python GIL 限制多线程吞吐；
4. **团队与生态协同**：项目同时有 Python AI 服务（yizhi-ai-module 负责 DeepSeek 调用）——**分工明确：Java 管业务与高并发通道，Python 管 AI 算法**，各取所长；
5. **运维简单**：单 JAR 部署 + systemd 管理，升级只需换 jar 重启，无需 Node 依赖树/虚拟环境；
6. **就业与人才**：Java 后端人才储备大，社区资料丰富，长期维护成本低。
- 补充：若项目以 AI 为核心（而非以稳定业务为核心），Python 才更合适；本项目是"物联网业务平台 + AI 增强"，Java 更匹配。

**43. 为什么选用 MySQL 存储业务数据，暂不接入 Redis？MQTT 与 HTTP 双协议搭配使用的理由是什么？**

**答：**

- **为什么 MySQL**：
  1. **业务强关系**：老人/家属/设备/告警/工单/通知高度关联，关系模型 + 外键语义（本项目逻辑关联）天然契合，JPA 映射成本低；
  2. **事务保证**：告警与通知、幂等记录与业务数据需要 ACID，MySQL InnoDB 成熟可靠；
  3. **运维熟悉**：团队 SQL 能力与云厂商托管（阿里云 RDS 可无缝迁移）成熟；
  4. **规模匹配**：当前演示/小规模数据量，单机 MySQL 完全够用，引入中间件反而增加复杂度。
- **暂不接 Redis 的理由**：① 当前读写压力低（QPS 小），MySQL 无瓶颈；② 减少架构复杂度与运维面（内存仅 1.6GB）；③ 项目处于功能完善阶段，优先保证业务正确性；④ 已规划在"设备在线状态、通知推送、热数据缓存、幂等去重"场景引入（见第 20 题），属于**按需引入而非一开始就上**。
- **MQTT + HTTP 双协议搭配理由**：
  - **MQTT（实时事件通道）**：发布订阅 + 低功耗长连接，适合海量设备持续上报（传感器、状态、事件）与云端反向指令（控制），QoS 保证关键消息；
  - **HTTP（请求-响应通道）**：适合前端管理查询、网关批量补传（可重试、可幂等）、图片上传（multipart）、命令轮询；
  - **两者互补**：实时/事件/控制走 MQTT（低延迟、省电），可靠/管理/大流量走 HTTP（易重试、易鉴权、易扩展），且双通道互为备份（Broker 挂了 HTTP 兜底，反之亦然）。

### E. 安全防护

**44. 边缘网关上报接口依靠 upload_id 实现幂等，如果 upload_id 被恶意伪造，会产生什么安全风险，如何防护？**

**答：**

- **可伪造的前提**：`POST /api/edge/data` **当前没有任何鉴权/签名校验**，任何人都可直接调用，upload_id 是客户端自报的字符串。
- **伪造风险**：
  1. **数据丢失（DoS）**：攻击者用目标设备**将要上报的 upload_id** 抢先调用成功（伪造任意数据），合法数据到达时被幂等拦截返回 duplicate → **合法数据被静默丢弃**，且可通过高频伪造大量 upload_id 阻塞数据接入；
  2. **脏数据注入**：伪造 upload_id + 伪造设备数据（如伪造 vitals/fall/sos）写入 sensor_data 与 alarm_event，**制造虚假告警/漏报**，干扰 AI 分析与工单派发；
  3. **存储耗尽**：海量随机 upload_id 灌入 `edge_ingest_record` 表，撑爆磁盘/拖慢查询；
  4. **数据重放**：截获合法请求后重复重放（同一 upload_id 幂等不产生新数据，但换新 upload_id 重放同内容可制造重复记录）。
- **防护方案**：
  1. **设备/网关签名**：请求头带 `Authorization: HMAC-SHA256(edge_id + upload_id + timestamp + secret)`，服务端用网关密钥验签（防篡改、防伪造）；
  2. **时间戳窗口校验**：`|now - received_at| < 5min` 拒绝过期重放；
  3. **upload_id 格式校验**：强制 UUID v4 格式（`@Pattern`），增加伪造成本并便于审计；
  4. **接口鉴权**：边缘接口走设备 Token（颁发给合法网关），与现有 Web 鉴权体系统一；
  5. **限流**：按 edge_id/IP 限流（Nginx/网关层），超阈值熔断；
  6. **审计日志**：记录每次上报的 edge_id/来源 IP，异常模式可追溯。

**45. 项目做了哪些安全防护？接口鉴权现状，存在哪些安全漏洞，后续如何加固？**

**答：**

- **已做的防护**：
  1. CORS 白名单（仅 elderlyweb.cn、localhost、120.27.129.78 等来源，allowCredentials=true）；
  2. 文件上传校验：MIME 类型白名单（image/jpeg/png/webp）、大小限制（10MB/50MB）、扩展名白名单；
  3. 参数级 Bean Validation（@NotBlank/@Pattern 等）；
  4. 登录返回 token 机制（`token-UUID` 形式）；
  5. 全局异常统一封装（不直接泄露堆栈，但 500 消息携带异常信息）。
- **当前鉴权现状与漏洞**：
  1. **无服务端 Token 校验**：token 只是 UUID 字符串，**没有任何拦截器校验**，所有接口（含管理端、边缘上报、AI）**均可匿名访问**；
  2. **密码明文存储与明文比较**：AuthService 直接 `password.equals(staff.getPassword())`，注册/重置都是明文（文档也注明开发环境如此）；
  3. **越权访问**：无权限模型，任意用户可查任意老人数据、处理任意告警；
  4. **无 HTTPS**：Nginx 仅 80 端口明文，口令与数据可被窃听；
  5. **无速率限制**：登录可暴力破解，接口可被刷；
  6. **错误信息泄露**：500 返回 `服务器内部错误: {异常消息}`，可能暴露表结构/堆栈细节；
  7. **命令队列内存存储**：重启丢失（可靠性问题）。
- **加固方案（按优先级）**：① 引入 Spring Security + JWT（真 JWT 签发/校验 + 拦截器，接口按角色放行）；② 密码 BCrypt 加密存储；③ Nginx 配置 HTTPS（免费证书）并 301 跳转；④ 登录限流 + 全接口限流；⑤ 边缘上报接口加 HMAC 设备签名（见第 44 题）；⑥ 统一错误信息脱敏；⑦ 审计日志（操作人、时间、IP）。

**46. 后端是否存在健康检查接口，可以检测哪些组件状态？**

**48. 后端日志存储在哪里？线上排查问题如何定位错误？是否配置异常告警能力？**

**答：**

- **日志存储**：① **systemd journal**：`sudo journalctl -u anxinban-backend`（标准输出/错误进 journal）；② **app.log**：项目根目录 `nohup` 输出文件（当前约 58MB，**无滚动/切分策略**，会无限增长）。无 logback 配置文件，无集中日志系统（无 ELK/Loki）。
- **线上排查流程**：① `journalctl -u anxinban-backend -f` 看实时日志；② `grep ERROR app.log` 定位异常；③ 按业务关键字串联——upload_id/alarmId/deviceId/elderId 是天然链路 ID，用它们关联"上报 → 处理 → 告警"全过程；④ 数据库侧查 edge_ingest_record/sensor_data 确认是否入库；⑤ 结合 /api/health 与 /api/ai/service-status 判断组件状态。
- **异常告警能力**：**未配置**。无日志监控、无邮件/钉钉/Webhook 告警，故障只能被动发现（用户反馈或 health 检查失败）。建议：① 接入 uptime 探活（Nginx + /api/health）；② 日志关键字（ERROR/MQTT 连接失败）告警；③ 进程守护已有（systemd Restart=always），缺的是"重启失败/频繁重启"的告警。

**49. Nginx 反向代理在本项目中承担了哪些职责？**

**答：**

1. **反向代理**：监听 80 端口，`proxy_pass http://127.0.0.1:8080`，把公网请求转发给 Java 后端——后端不直接暴露公网端口；
2. **域名绑定**：server_name `elderlyweb.cn www.elderlyweb.cn _`（默认服务器兜底），对外统一入口；
3. **端口收敛**：用户只需访问 80，8080 仅监听内网；
4. **静态资源中转**：`/uploads/**` 经后端静态映射提供（Nginx 转发），未来可直接加 `location /uploads` 让 Nginx 直出文件，减轻 Java 负担；
5. **可扩展职责（当前未启用）**：HTTPS 终结（证书）、gzip 压缩、静态缓存、客户端限流（limit_req）、多实例负载均衡（upstream）、WAF 规则。
- 当前未配置：HTTPS、gzip、限流、upstream 负载均衡（单实例）。

### G. AI 模块

**50. 后端 AI 模块采用双轨降级机制，请讲清楚降级的触发条件与返回结果。**

**答：**

- **双轨**：① 主轨——外部 Python AI 服务（`http://127.0.0.1:8000`，内部对接 DeepSeek 大模型）；② 备轨——Java 本地规则引擎/Mock 逻辑（零外部依赖，保证接口永远可用）。
- **触发条件**（满足任一即降级，`AiForwardService.forward` 返回 null）：
  1. `ai.service.base-url` 未配置（为空）→ 直接走 fallback；
  2. `ai.service.enable-forward=false`（配置强制关闭）；
  3. 外部 AI **超时**（`ai.service.timeout-seconds=15`，HTTP 请求超时）；
  4. 连接拒绝/服务不可达（ConnectException）；
  5. 返回非 200 状态码；
  6. 响应体 JSON 解析失败。
- **降级后的返回结果**：
  - **接口结构完全一致**（客户端无感）：health-analysis 返回 risk_level/risk_reason/need_alarm/suggestion/family_notice/community_suggestion/need_work_order 等；chat/quick 返回 intent/quick_reply/need_alarm；rag-query 返回 answer/confidence/retrieved_knowledge；vision-analysis 返回 vision_result/confidence；
  - **每条响应带 `source` 字段标识轨道**：`python_ai_service`（主轨）或 `java_rule_fallback`/`java_local_rule`/`java_mock_deep`/`java_mock_rag`/`java_mock_vision`（备轨），前端/监控可感知；
  - **兜底升级逻辑**：健康上传时只要 fall_status 含"跌倒"，无论 AI 结论如何都强制 need_alarm=true、risk_level=高风险（`fallback-upgrade`，防止 AI 漏判致命事件）；
  - 暴露 `GET /api/ai/service-status` 返回 `current_mode`（python_ai_service / java_fallback），供监控与演示展示降级状态。

### H. 代码规模

**51. 项目业务代码量大概多少，哪些为自研业务代码，哪些使用开源第三方库？**

**答：**

- **代码量**：`src/main/java` 约 **3.4 万行 Java**（含 Javadoc 注释，34,096 行），不含测试；约 230+ 个类文件；另有测试类、SQL 脚本、Python 模拟脚本若干。
- **自研业务代码**（占比绝大部分）：全部业务逻辑均为自研——
  - Controller（42 个）、Service（40+ 个）、Entity（40 个）、Mapper Repository（40 个）、DTO（30+ 个）；
  - MQTT 模块（客户端封装、主题常量、消息消费者、规则引擎、设备模拟器）；
  - 全局配置（数据源、CORS、静态资源、异常处理）、种子数据/模拟脚本。
- **开源第三方库**（pom.xml 依赖）：Spring Boot 4.0.6（webmvc/restclient/data-jpa/validation）、Spring Data JPA、HikariCP（随 data-jpa）、Eclipse Paho MQTT 1.2.5、Jackson 2.18.5（databind/core/annotations/jsr310）、MySQL Connector/J 8.0.33、Jakarta Validation/Annotation、Maven 构建工具；Spring Boot 默认 Jackson 3.x 被显式排除（项目统一 Jackson 2.x）。
- 说明：无第三方支付/推送/OSS SDK 等，AI 调用与文件存储均为自研 HTTP 对接，可扩展性靠后续引入 SDK 完善。
